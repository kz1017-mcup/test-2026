# 🔬 第10回：Reverse Engineering：バイナリの中身を解き明かせ

> 📌 **この第10回について**
> 第9回までで、本番のCTFに向けた基本の学習は一区切りです。この第10回は、**本番でより良い成績を残すための追加テキスト**です。
> 本番では、これまで学んだカテゴリ（Web・Crypto・Network・OSINT・Forensics・PWN）**以外に、RE（リバースエンジニアリング）が出題される可能性があります**。余裕のある方は、本番前にぜひ取り組んでみてください。

今回は「Reverse Engineering（リバースエンジニアリング）」、略して**RE**に挑戦します。一言でいうと、**「ソースコードのない実行ファイル（バイナリ）を渡されて、中で何が行われているかを解き明かす」**ジャンルです。

今回は、ソースコードが**ありません**。手元にあるのは、`0`と`1`の塊である実行ファイルだけ。そこから**プログラムの設計図を復元する**のが、今回の仕事です。

#### 🧭 REの2つの武器：静的解析と動的解析

バイナリを調べる方法は、大きく2つに分かれます。

| 解析の種類 | 何をするか | 例えるなら | 今回使う道具 |
| --- | --- | --- | --- |
| **静的解析** | プログラムを**実行せずに**、中身（命令の並び）を読む | 機械を分解して、設計図を読む | `strings`、`objdump`、**Ghidra** |
| **動的解析** | プログラムを**実際に動かしながら**、途中の状態を観察する | 機械を動かして、途中で一時停止して中を覗く | **gdb**（デバッガ） |

実際のREでは、この2つを**行ったり来たり**します。「静的に読んで仮説を立て、動的に動かして確かめる」というのが基本の型です。

#### 🔑 今回の一貫したテーマ：「プログラムは、中身を隠しきれない」

プログラムは最終的にCPUが実行できる形になっている以上、**答えはどこかに必ず書かれています**。難読化や工夫で隠していても、それを読み解くための道具と考え方さえあれば、辿り着くことができます。

今回は3問を、次の順で解いていきます。

* **第1問（静的解析）**：実行ファイルの中から、組み立てられるフラグを読み出す
* **第2問（動的解析）**：プログラムを途中で止めて、CPUの中身を直接覗く
* **第3問（静的解析）**：Ghidraで逆コンパイルして、条件分岐を読み解く

#### 🛠️ 今回使う道具について

* **Ghidra**：静的解析の定番ツールです。バイナリを人間が読める形（C言語に近い疑似コード）に**逆コンパイル**してくれます。本講座では、**手元のPCにインストール済みの前提**で解説します（インストール方法は別途ご案内します）。
* **CyLabのWebシェル**：第2回で準備したブラウザ上のLinux環境です。`strings`・`objdump`・`gdb`・`nc` が使えます。**Ghidra以外の解析は、WebシェルとCyberChefだけでも完結できます**。
* **CyberChef**：16進数と文字の相互変換などに使います（第4回で登場）。

> ⚠️ **注意：CyLabのWebシェルには、Ghidraと`ltrace`（ライブラリ呼び出しの追跡ツール）は入っていません。** Ghidraは手元のPCで使ってください。

> 📝 **フラグの形式について**
> 今回の3問は、フラグが `picoCTF{...}` ではなく **`academy{...}` の形式**で出題されています（CyLab独自の形式です）。**さらに、`{}`の中の末尾に付くランダムな文字列は、受講者ごとに異なる場合があります**。本文中の「答え合わせ」では、その部分を `xxxxxxxx` と伏せて表示しますので、ご自身で求めた値と照らし合わせてください。

## 📝 第1問：ASCII FTW (CyLab - Medium)

### 1. 前提知識：実行ファイルの中身と、`strings`の限界

#### 🧩 バイナリとは何か

私たちが書いたプログラム（ソースコード）は、**コンパイル**という作業でCPUが直接実行できる**機械語**の塊（バイナリ）に変換されます。ソースコードにあった変数名やコメントは、コンパイルの過程でほとんど失われます。

機械語は人間には読めないので、これを**アセンブリ言語**（`mov`、`push`、`call` といった短い命令の並び）の形に書き直して読むのが基本です。この変換を**逆アセンブル（ディスアセンブル）**といい、アセンブリ言語をさらにC言語に近い形に復元することを**逆コンパイル**といいます。

#### 🔎 `strings`で見つからないフラグ

第7回で学んだ`strings`コマンドは、ファイルの中から「**人間が読める連続した文字列**」を取り出すツールでした。パスワードやフラグが**そのまま文字列として埋め込まれている**プログラムなら、これだけで見つかります。

ところが、プログラムが**1文字ずつ命令の中に埋め込んで、実行時に組み立てている**場合は話が変わります。たとえば次のようなコードです。

```c
char flag[40];
flag[0] = 'a';   // 0x61
flag[1] = 'c';   // 0x63
flag[2] = 'a';   // 0x61
...
```

この場合、`'a'`や`'c'`は**命令の一部**として埋め込まれているだけで、データとして並んだ文字列にはなりません。`strings`の網には引っかからないのです。

#### 🔢 ASCIIコードと16進数

コンピュータは文字を数字で扱います。この対応表が**ASCIIコード**です。たとえば小文字の`a`は、16進数で`0x61`です（`0x`は「これは16進数です」という目印）。

| 文字 | 16進数 | 文字 | 16進数 |
| --- | --- | --- | --- |
| `a` | `0x61` | `{` | `0x7b` |
| `c` | `0x63` | `}` | `0x7d` |
| `d` | `0x64` | `0`〜`9` | `0x30`〜`0x39` |

この対応は、CyberChefの「From Hex」で一括変換できます。

* `strings`でフラグを探してみましょう。見つかりますか？（見つからないのが、この問題のポイントです）
* 「逆アセンブルする」とは、実行ファイルの中の命令を読める形にすることです。`main`関数を探して、中の命令を眺めてみましょう。
* 英数字を表す16進数は、`0x30`〜`0x7a`の範囲に収まります。

### 4. 詳細な解説（解き方）

#### 🛠️ ステップ1：まず動かしてみる（動的な様子見）

ファイルをWebシェルにダウンロードして、実行してみます。

```bash
chmod +x asciiftw
./asciiftw
```

```
The flag starts with 61
```

「フラグは`61`で始まる」と表示されます。`61`は、先ほどの表で見た通り**`a`のASCIIコード**です。つまり、このプログラムは**フラグの1文字目の16進数だけを表示している**ことが分かります。全文は表示してくれません。

#### 🛠️ ステップ2：`strings`で探す（そして、失敗する）

```bash
strings asciiftw | grep -i pico
```

結果は**ゼロ件**です。`academy`で検索しても見つかりません。フラグはプログラムの中に**文字列としては存在していない**のです。

#### 🛠️ ステップ3：逆アセンブルして、命令を読む

`main`関数を逆アセンブルします。Webシェルでは`objdump`が使えます。

```bash
objdump -d -M intel --no-show-raw-insn asciiftw
```

`main`の中に、次のような命令が並んでいます（抜粋です）。

```
mov    BYTE PTR [rbp-0x30],0x61
mov    BYTE PTR [rbp-0x2f],0x63
mov    BYTE PTR [rbp-0x2e],0x61
mov    BYTE PTR [rbp-0x2d],0x64
mov    BYTE PTR [rbp-0x2c],0x65
mov    BYTE PTR [rbp-0x2b],0x6d
mov    BYTE PTR [rbp-0x2a],0x79
mov    BYTE PTR [rbp-0x29],0x7b
...
```

`mov A, B` は「**AにBを代入する**」という命令です。ここでは、スタック上の連続した場所（`rbp-0x30`、`rbp-0x2f`、…）に、`0x61`、`0x63`、`0x61`…と**1バイトずつ値を書き込んで**います。これこそが、**フラグを1文字ずつ組み立てている**処理の正体です。

書き込まれている値（`0x61, 0x63, 0x61, 0x64, 0x65, 0x6d, 0x79, 0x7b, …`）を順に文字へ変換すると、`a, c, a, d, e, m, y, {, …` となり、`academy{` で始まっていることが分かります。`main`には、この種の`mov`命令が**ずらりと**並んでいます（フラグの長さの分だけ続きます）。

#### 🎯 答え合わせ

**Flag:** `academy{ASCII_IS_EASY_xxxxxxxx}`

（`xxxxxxxx`は受講者ごとに異なる値です）

`strings`では見つからなかったフラグが、**命令を読むだけで**姿を現しました。これが静的解析の基本です。「実行しなくても、プログラムの中に答えは書いてある」ことが体感できたと思います。

> 💡 **実務に繋がるポイント：**
> 今回のように「文字を1文字ずつ命令の中で組み立てる」手法は、**マルウェア（不正プログラム）が`strings`による調査から逃れるために実際に使う手口**で、「スタック文字列（stack strings）」と呼ばれます。マルウェア解析の現場では、`strings`で何も出てこないからといって安全とは判断せず、逆アセンブラや逆コンパイラ（Ghidraなど）で中身を確認するのが基本です。

## 📝 第2問：GDB baby step 1 (CyLab - Medium)

### 1. 前提知識：レジスタと、デバッガによる動的解析

#### 🧠 CPUの中の「作業机」＝レジスタ

CPUは、計算の途中結果を**レジスタ**と呼ばれる超高速の小さな記憶領域に置いて作業します。メモリが「倉庫」なら、レジスタは「作業机の上」です。

今回登場するのは次のレジスタです。

| レジスタ | 役割 |
| --- | --- |
| **`eax`** | 計算結果や、**関数の戻り値**を入れる場所（今回の主役） |
| `rbp` / `rsp` | スタック（関数が使うメモリ領域）の位置を指す |

関数が終わるとき、その**戻り値は`eax`に入れて返す**のが決まりです。つまり、**`main`関数の最後の時点で`eax`に何が入っているか**は、「`main`が最終的に何を返したか」と同じ意味になります。

#### 🐞 デバッガ（gdb）で、プログラムを途中で止める

**gdb**は、プログラムを実行しながら、**好きな場所で一時停止**して、レジスタやメモリの中身を見られるツールです。

| gdbのコマンド | 意味 |
| --- | --- |
| `disassemble main` | `main`関数を逆アセンブルして表示する |
| `break *アドレス` | 指定した命令の**直前**で止まるように、ブレークポイントを置く |
| `run` | プログラムを実行する（ブレークポイントで止まる） |
| `print $eax` | `eax`レジスタの中身を表示する |

プログラムを**実際に動かして**状態を観察する、これが動的解析です。

### 3. ヒント

* まず、配布されたファイルを`gdb`で開いて、`main`関数を逆アセンブルしてみましょう。
* アセンブリを読んで「`eax`に何が代入されているか」を計算で求めることもできますし、**実際に動かして`eax`の値を見る**こともできます。両方試して、答えが一致するか確かめてみましょう。
* 答えは**10進数**で提出します。16進数のまま出さないよう注意しましょう。

### 4. 詳細な解説（解き方）

#### 🛠️ ステップ1：`main`を逆アセンブルする（静的に読む）

Webシェルにファイル（`debugger0_a`）をダウンロードして、gdbで開きます。

```bash
chmod +x debugger0_a
gdb ./debugger0_a
```

```
(gdb) set disassembly-flavor intel
(gdb) disassemble main
```

```
Dump of assembler code for function main:（アドレスの表示は省略しています）
   <+0>:     endbr64
   <+4>:     push   rbp
   <+5>:     mov    rbp,rsp
   <+8>:     mov    DWORD PTR [rbp-0x4],edi
   <+11>:    mov    QWORD PTR [rbp-0x10],rsi
   <+15>:    mov    eax,0x86342
   <+20>:    pop    rbp
   <+21>:    ret
End of assembler dump.
```

読むべきは**終わり近くの数行**だけです。

* `mov eax,0x86342`：`eax`に`0x86342`を代入する
* `pop rbp`、`ret`：関数を終えて、呼び出し元に戻る

`ret`で戻る直前に、`eax`には**`0x86342`**が入っていることが分かります。冒頭の`push`や`mov`は、関数を始めるときの決まり文句で、今回の答えには関係ありません。

`0x86342`は16進数です。問題は**10進数**での提出を求めているので、変換が必要です。**CyberChefの「From Base」**（`Radix`を`16`にする）に、`0x`を除いた`86342`を入力すると、10進数に変換できます（電卓アプリの「プログラマー」モードでも変換できます）。

#### 🛠️ ステップ2：実際に動かして確かめる（動的解析）

静的に読んで出した答えを、**実際に動かして**確かめます。`ret`の直前（`<+21>`）にブレークポイントを置いて、プログラムを実行します。

```
(gdb) break *main+21
(gdb) run
(gdb) print $eax
$1 = 549698
(gdb) print/x $eax
$2 = 0x86342
```

プログラムが`ret`の直前で止まり、`eax`の中身が**549698**（16進で`0x86342`）と表示されます。静的に読んで計算した値と**一致しました**。

#### 🎯 答え合わせ

**Flag:** `academy{549698}`

> 💡 **実務に繋がるポイント：セキュリティの現場での動的解析**
> 怪しいファイル（マルウェアの疑いがある実行ファイルなど）が見つかったとき、セキュリティの現場では、**隔離した環境で実際に動かして、振る舞いを観察する**動的解析がよく行われます。通信先や作成するファイルなどを記録して、被害範囲の調査や、侵害の痕跡（IOC）の洗い出しに活用します。
> 暗号化やパック（圧縮）で隠された情報も、動かして止めると、メモリやレジスタ上で平文になることがあります。今回の「止めて、見る」操作が、その基本形です。
> ⚠️ 動的解析は**実際にプログラムを実行する**ため、疑わしいファイルは、必ず仮想マシンなどの隔離環境で、ネットワークも制限して実行します。

## 📝 第3問：Gatekeeper (picoCTF 2026 - Medium)

### 1. 前提知識：逆コンパイラで「条件分岐」を読み解く

#### 🚪 プログラムは「条件分岐」でできている

プログラムの動きを決めるのは、突き詰めると「**もし〜なら、〜する。そうでなければ、〜する**」という条件分岐（`if`文）の連なりです。REでは、**「どんな入力のとき、どの分岐に進むか」を読み解く**ことが、問題を解くカギになります。

Ghidraのような逆コンパイラは、アセンブリのジャンプ命令（`cmp`、`jg`、`jle`など）の羅列を、`if`文を使ったC言語に近い形に復元してくれます。条件を**人間の言葉で読める**ので、条件に合う入力を逆算できます。

#### 🏷️ 関数名が残っている：シンボル情報

コンパイルの際に関数名などの情報（**シンボル**）が削られていないバイナリは、Ghidraの関数一覧に`main`以外にも**意味のある名前**が並びます。名前だけで、プログラムの構造の見当が付きます。

今回のバイナリには、`main`のほかに次の関数があります。

* `is_valid_decimal`：10進数として正しいかを調べる関数
* `is_valid_hex`：16進数として正しいかを調べる関数
* `reveal_flag`：**フラグを表示する関数**

この名前を眺めるだけで、「`reveal_flag`が呼ばれる条件を探せばよい」という方針が立ちます。

#### 🔢 16進数で数を書く

`1000`のような普通の数字は10進数です。16進数では、`0`〜`9`に加えて`a`〜`f`（10〜15）を使います。同じ数でも、書き方によって**文字数が変わります**。

| 10進数 | 16進数 |
| --- | --- |
| 1000 | `3e8`（3文字） |
| 4095 | `fff`（3文字） |
| 65535 | `ffff`（4文字） |

この「文字数が変わる」という性質が、今回のカギになります。

### 2. 問題文

<https://learn.cylabacademy.org/library/731>

> **【問題】 Gatekeeper**
> What's behind the numeric gate? You only get access if you enter the *right* kind of number. You can download the program file here. Reverse the program behavior and find what input grants access to the secret flag. `nc <ホスト> <ポート>`

### 3. ヒント

* まずはプログラムをダウンロードして、手元（Webシェル）で動かしてみましょう。いろいろな数字を入れると、どんなメッセージが出ますか？
* 「Ghidra」「IDA Free」「Radare2」といった逆コンパイラ・逆アセンブラで、`main`関数の条件分岐を読み解きましょう。
* 出力が分かりにくい場合は、**文字列を逆順にする**ことや、**余計な文字を取り除く**ことを考えてみましょう。

### 4. 詳細な解説（解き方）

#### 🛠️ ステップ1：まず動かして、反応を観察する

ファイルをWebシェルにダウンロードして、いろいろな入力を試します。

```bash
chmod +x gatekeeper
echo 500 | ./gatekeeper
```

入力を変えて何度か試すと、次のような反応が得られます。

| 入力 | 表示されるメッセージ |
| --- | --- |
| `500` | `Too small.` |
| `1000` | `Access Denied.` |
| `99999` | `Too high.` |
| `ffff` | `Too high.` |

プロンプトには「must be > 999」（999より大きいこと）とあります。`1000`は範囲内のはずなのに、`Access Denied.`（拒否）になっています。**範囲だけでは足りない、別の条件がある**ことが分かります。また、`ffff`（16進数）も受け付けられている点に注目しましょう。

#### 🛠️ ステップ2：`strings`で、手がかりを集める

```bash
strings gatekeeper
```

`Enter a numeric code (must be > 999 ):`、`Invalid input.`、`Too small.`、`Too high.`、`Access Denied.`、`Access granted:`、`/flag.txt` といった文字列が見つかります。`/flag.txt`を読んで`Access granted:`と表示する処理が、どこかにあるようです。

#### 🛠️ ステップ3：Ghidraで`main`を読む

ここで、今回の講座で**初めてGhidraを使います**。Webシェルではなく、**手元のPC**で操作します。

**【Ghidraの基本手順】**

1. **ファイルを手元のPCに保存する**：問題ページの「here」のリンクから、`gatekeeper`をダウンロードします。
2. **Ghidraを起動して、プロジェクトを作る**：メニューの `File` → `New Project…` を選び、`Non-Shared Project`（ひとり用）で、好きなプロジェクト名を付けて作成します。
3. **ファイルを取り込む**（インポート）：`File` → `Import File…` で、保存した`gatekeeper`を選びます。形式は自動で認識されるので、そのまま`OK`を押します。取り込み結果の画面（Import Results Summary）が出たら、`OK`で閉じます。
4. **解析ツールを開く**：プロジェクトの画面に`gatekeeper`が表示されるので、**ダブルクリック**します。解析ツール（**CodeBrowser**）が開き、「解析しますか？」と聞かれるので`Yes`、続けて表示される画面もそのまま`Analyze`を押します。右下の進捗バーが消えたら、解析完了です。
5. **画面の見方**：CodeBrowserは、主に3つの領域に分かれています。

| 場所 | 名前 | 内容 |
| --- | --- | --- |
| 左 | **Symbol Tree**（シンボルツリー） | 関数などの名前の一覧。`Functions`の中に関数が並ぶ |
| 中央 | **Listing**（リスティング） | 逆アセンブル結果（アセンブリ言語の命令の並び） |
| 右 | **Decompile**（デコンパイル） | **C言語に近い形に復元されたコード**（今回のメイン） |

6. **`main`を開く**：左側のSymbol Treeで`Functions`を開くと、`is_valid_decimal`、`is_valid_hex`、`reveal_flag`、`main` といった、意味の分かる名前が並びます。**`main`をダブルクリック**すると、右側のDecompileウィンドウに、`main`関数の中身が表示されます。

> 🔎 **【要確認：Ghidraの画面】** 上記の手順の、メニュー名・ボタン名・ウィンドウ名が、実際のGhidraの画面と合っているかを確認してください。また、Decompileウィンドウの変数名（`local_38`のような仮の名前）や、条件式の表記も、実際の画面で確認して、以下の疑似コードと対応づけて書き直してください。

`main`の中身は、次のような処理に整理できます（アセンブリを読み解いた結果を、C言語風にまとめたものです）。

```c
scanf("%31s", buf);                    // 入力を文字列として受け取る
len = strlen(buf);                     // 入力の「文字数」を数える
value = -1;

if (is_valid_decimal(buf)) {
    value = atoi(buf);                 // 10進数として解釈
} else if (is_valid_hex(buf)) {
    value = strtol(buf, NULL, 16);     // 16進数として解釈
} else {
    puts("Invalid input.");
    return 1;
}

if (value <= 999)        puts("Too small.");
else if (value > 9999)   puts("Too high.");
else if (len == 3)       reveal_flag();        // ← フラグはここ！
else                     puts("Access Denied.");
```

この条件分岐を、上から順に読み解いていきます。

1. **まず10進数として正しいかを調べ、違えば16進数として調べる**（判定の**順番**に注目）
2. 数値が**999以下**なら`Too small.`
3. 数値が**9999より大きい**と`Too high.`
4. 1000〜9999の範囲に入っていても、**入力の文字数がちょうど3文字**のときだけ`reveal_flag()`（フラグ表示）が呼ばれる。それ以外は`Access Denied.`

#### 🛠️ ステップ4：条件を満たす入力を逆算する

`reveal_flag`が呼ばれる条件を整理します。

* **値が1000〜9999**であること
* **入力の文字数が3文字**であること

3文字の**10進数**だと、最大でも`999`です。これでは`Too small.`になってしまいます。一方、**16進数**なら、3文字でも`3e8`（=1000）〜`fff`（=4095）まで表せます。つまり、「**3文字の16進数**」が、この門の「*正しい種類の数字*」です。

さらに注意が必要です。判定は**10進数を先に調べる**ので、`400`のように数字だけで書くと**10進数として扱われて**しまい、400と解釈されます。**`a`〜`f`の文字を1つ以上含める**必要があります。

**答え：`3e8`**（`3e8`〜`fff`の範囲の、アルファベットを含む3文字の16進数なら、どれでも可）

#### 🛠️ ステップ5：インスタンスに接続して、フラグを取得する

問題ページで「Launch Instance」を押すと、`nc`のホスト名とポート番号が表示されます。Webシェルで、その接続先に`nc`で接続します。

```bash
nc <ホスト> <ポート>
```

接続すると、プログラムのプロンプトが表示されます。**プロンプトが出たら、ステップ4で求めた`3e8`を入力して、Enterキーを押します。**

```
Enter a numeric code (must be > 999 ): 3e8
Access granted: }xxxxxxxxftc_oc_ip...{ymeftc_oc_ipdacaftc_oc_ip
```

`Access granted:`の後ろに、文字がでたらめに並んだ文字列が表示されます。よく見ると、**`ftc_oc_ip`という同じ文字列が何度も繰り返されて**います。ヒントにあった「逆順にして、余計な文字を取り除く」を、手作業で実行してみましょう。

1. **`Access granted:`の後ろの文字列を、逆順にする**
   * `ftc_oc_ip`を逆から読むと、**`pi_co_ctf`**になります
   * 例：末尾の`{ymeftc_oc_ipdacaftc_oc_ip`を逆順にすると、`pi_co_ctfacadpi_co_ctfemy{`になります
2. **逆順にした文字列から、`pi_co_ctf`を取り除く**
   * 例：`pi_co_ctfacadpi_co_ctfemy{`から`pi_co_ctf`を取り除くと、`academy{`が現れます

この2つの操作を、文字列全体に行うと、フラグが復元できます。（CyberChefの「Reverse」と「Find / Replace」を使うと、手作業で間違えずに行えます）

#### 🎯 答え合わせ

**Flag:** `academy{3_digit_hex_GT_999_xxxxxxxx}`

（`xxxxxxxx`は受講者ごとに異なる値です）

> 💡 **実務に繋がるポイント：**
> 「どんな入力のとき、どの処理に進むか」を読み解く作業は、ソースコードのないソフトウェアの**脆弱性調査**や、**マルウェアの動作解析**そのものです。たとえば、不正なプログラムが**特定の条件でだけ悪さをする**仕組みは、条件分岐の中に隠れています。逆コンパイラ（Ghidraなど）でその条件を読み解く力は、セキュリティの現場で、標的型攻撃やランサムウェアの調査を行うマルウェアアナリストの基本スキルです。

## 📅 第10回のまとめ

今回はRE（リバースエンジニアリング）の基本となる**静的解析**と**動的解析**を体験しました。

* **静的解析**（第1問）：実行せずに中身を読む。`strings`では見つからなくても、逆アセンブル（`objdump`）で、命令の中に埋め込まれた文字を読み出せる
* **動的解析**（第2問）：gdbでプログラムを途中で止めて、レジスタ（`eax`）の中身を直接見る。静的に読んで求めた答えを、動かして確かめられる
* **静的解析・逆コンパイル**（第3問）：Ghidraで逆コンパイルして、条件分岐を読み解く。「どんな入力のとき、どの処理に進むか」を、コードを読むだけで逆算できる

3問を通して共通していたのは、**「ソースコードがなくても、バイナリの中に答えは書かれている」**という点です。
